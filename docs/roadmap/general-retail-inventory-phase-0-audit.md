> **هدف:** ثبت رفتار واقعی فعلی پیش از شروع تغییرات اجرایی برای تبدیل LyraPOS به سیستم عمومی فروشگاهی.  
> **مبنای بررسی:** شاخه `main` در commit پایه PR #22، یعنی `49a7dae6af511df6a5ea680ce1d3720c1b3b85eb`.  
> **نوع بررسی:** بازبینی ایستای فایل‌های اصلی و تست‌های موجود در GitHub؛ در این مرحله کد اجرا یا تغییر داده نشده است. این سند «نتیجه ممیزی مسیرهای بررسی‌شده» است، نه ادعای حذف/بررسی تک‌تک ارجاع‌های repository. پیش از حذف کد در فازهای بعدی، جست‌وجوی سراسری روی head روز شاخه و بررسی همه نتایج الزامی است.

## 1. خلاصه مدیریتی

فاز صفر نشان داد که قابلیت‌های موردنیاز تا حدی از قبل وجود دارند، اما هنوز مسیرهای اجرایی موازی و وابستگی‌های رستورانی مهمی باقی مانده‌اند:

1. **موجودی مستقیم محصول و دفتر گردش آن وجود دارد** و باید مبنای کار بماند؛ لازم نیست سیستم موجودی از نو طراحی شود.
2. **موجودی منفی در وضعیت فعلی مجاز نیست.** سرویس مرکزی موجودی به‌صورت صریح مانع کاهش زیر صفر می‌شود و خطای `Insufficient stock` برمی‌گرداند. تست موجود نیز این رفتار را انتظار دارد.
3. **اصلاح دستی موجودی محصول از قبل API و ledger دارد**؛ باید همان مسیر تکمیل و به UI انبار وصل شود تا دو منبع حقیقت ایجاد نشود.
4. **Recipe/Supplies در چرخه واقعی سفارش فعال‌اند**: ساخت snapshot هنگام فروش/افزودن قلم، کاهش مواد اولیه، و برگشت آن هنگام لغو. فقط حذف صفحه یا route کافی نیست.
5. **میز به ثبت سفارش، سفارش‌های نگه‌داشته‌شده، گزارش‌ها، هزینه‌ها و KDS وصل است.** پنهان‌کردن لینک میز از سایدبار وابستگی backend را حذف نمی‌کند.
6. **KDS را می‌توان حفظ کرد.** احراز هویت، WebSocket، نمایش مستقل و routing بر اساس دسته/ایستگاه وجود دارند؛ بااین‌حال، مسیرهای متعددی هنوز به `tables` و `table_id` برای تخصیص ایستگاه و نمایش نام میز متکی‌اند.
7. دیتابیس از مهاجرت‌های ترتیبی استفاده می‌کند و در کد فعلی آخرین نسخه ثبت‌شده **99** است. مهاجرت‌های منتشرشده نباید ویرایش شوند.
8. تست‌های فعلی رفتارهای مهمی را تثبیت کرده‌اند؛ به‌ویژه تست موجودی که منفی‌بودن موجودی مطلق را رد می‌کند، تست چرخه Recipe، تست held orders و تست هزینه میز. این‌ها باید با تصمیم محصول تطبیق داده شوند، نه اینکه assertionها صرفاً برای سبزشدن حذف شوند.

## 2. موجودی مستقیم محصول: وضعیت فعلی

### فایل‌ها و مسئولیت‌ها

- `main/services/inventory.ts`: `resolveInventoryDeduction`، `adjustProductStock` و خواندن دفتر گردش.
- `main/routes/inventory.ts`: API تاریخچه `/api/inventory/movements`.
- `main/routes/products.ts`: اعتبارسنجی محصول و APIهای اصلاح موجودی محصول.
- `frontend/src/app/(dashboard)/products/page.tsx`: فرم محصول.
- `frontend/src/app/(dashboard)/inventory/page.tsx`: صفحه‌ای که در حال حاضر عمدتاً بر پایه supplies و recipes است.
- `tests/inventory-ledger.test.ts`: تست دفتر گردش، افزایش/کاهش دستی و سازگاری مهاجرت.

### رفتار ثبت‌شده در کد

- `products.stock_quantity` موجودی فعلی/کش‌شده محصول است و `track_inventory` مشخص می‌کند فروش از موجودی آن محصول کسر شود یا نه.
- `resolveInventoryDeduction` ابتدا ارتباط محصول به محصول را بررسی می‌کند؛ اگر `inventory_product_id` تنظیم شده باشد، مقدار کسر با `inventory_deduction_quantity` ضرب می‌شود. در غیر این صورت، اگر `track_inventory` فعال باشد، از خود محصول کسر می‌شود.
- اعتبارسنجی ارتباط محصول به محصول در `main/routes/products.ts` اجازه خودارجاعی، زنجیره چندمرحله‌ای یا چند محصول فروشنده برای یک هدف موجودی را نمی‌دهد. این محدودیت‌ها بخشی از رفتار فعلی‌اند و نباید هنگام حذف Recipe ناخواسته از بین بروند.
- `adjustProductStock` موجودی را به‌روزرسانی و سپس یک ردیف `inventory_movements` با مقدار تغییر مؤثر، نوع حرکت، علت، کاربر، ارجاع و `stock_after` ثبت می‌کند. مستندات خود تابع می‌گویند مرز تراکنش را caller باید فراهم کند.
- دفتر گردش شامل فیلدهای provenance/import نیز هست؛ بازنویسی صفحه یا migration نباید این اطلاعات را حذف کند.
- API موجودی دستی محصول از قبل در تست با مسیر `/api/products/:id/stock` استفاده می‌شود. افزایش/کاهش و تعیین موجودی نهایی از طریق این مسیر، گردش `adjustment` می‌سازند. پس مسیر مطلوب، گسترش/استفاده مجدد از این API و ledger است، نه نوشتن مستقیم `stock_quantity` از صفحه جدید.

### یافته بحرانی: موجودی منفی در چند لایه مسدود شده است

- در `adjustProductStock` شرط SQL شامل کنترل `COALESCE(stock_quantity, 0) + delta >= -tolerance` است؛ اگر موجودی از صفر پایین‌تر برود، update انجام نمی‌شود و خطای `Insufficient stock` صادر می‌شود.
- مسیر ایجاد سفارش در `main/routes/orders.ts` این خطا را به‌عنوان شکست اعتبارسنجی موجودی گزارش می‌کند؛ بنابراین فروش بیش از موجودی می‌تواند ثبت سفارش را متوقف کند.
- `PRODUCT_NUMERIC_FIELDS` در `main/routes/products.ts` برای `stock_quantity` حداقل صفر دارد.
- تست `tests/inventory-ledger.test.ts` درخواست کاهش دستی بیش از موجودی را انتظار دارد که شکست بخورد و مقدار قبلی حفظ شود؛ همچنین `PUT` با `stock_quantity: -1` را با پاسخ 400 رد می‌کند.
- ساختار فعلی جدول products ستون `stock_quantity REAL DEFAULT 0` دارد؛ در تعریف اولیه مشاهده‌شده CHECK صریح برای غیرمنفی‌بودن این ستون نیست، ولی سرویس و API آن را تحمیل می‌کنند.

**اثر روی طراحی:** برای تحقق تصمیم فروش با موجودی منفی باید حداقل منطق سرویس و تست‌های API اصلاح شوند. قبل از تغییر، باید قرارداد موجودی منفی در عملیات فروش، اصلاح دستی و تعیین موجودی نهایی یکسان و روشن شود. تست‌های فعلی باید تغییر رفتاری را صریحاً منعکس کنند؛ نباید تست‌ها حذف یا تضعیف شوند.

## 3. فروش، افزودن قلم، لغو و برگشت

### مسیرهای کشف‌شده

- `main/routes/orders.ts`: ثبت سفارش، افزودن قلم به سفارش موجود، لغو سفارش، لغو/بازگردانی قلم، تغییر وضعیت و محاسبات مالی.
- `main/routes/index.ts`: مسیرهای دیگری برای لغو/برگشت موجودی و Recipe در مسیرهای سفارش/قلم.
- `main/services/orders.ts`: محاسبه مجموع اقلام فعال؛ این سرویس خود مسئول تغییر موجودی نیست.
- `main/routes/refunds.ts` و مسیرهای bills نیز باید در فاز اجرا بررسی شوند تا برگشت مالی از برگشت فیزیکی موجودی اشتباه گرفته نشود.

### رفتار فعلی مهم

- هنگام ایجاد سفارش و افزودن اقلام به سفارش، سیستم `resolveInventoryDeduction` را اجرا می‌کند، `inventory_deducted_quantity` و `inventory_product_id` را روی ردیف سفارش ذخیره می‌کند و سپس از موجودی محصول کسر می‌کند.
- همان دو مسیر، `buildRecipeSnapshot` و `applyRecipeSnapshot` را هم فراخوانی می‌کنند تا مواد اولیه کم شوند.
- لغو قلم و لغو سفارش، بر اساس مقدار و محصول ثبت‌شده روی قلم سفارش، موجودی محصول را برمی‌گردانند؛ همچنین snapshot مواد اولیه را restore می‌کنند.
- مسیر void با مسیر cancel یکسان نیست: کد فعلی برای void توضیح صریح دارد که موجودی کسرشده را restore نمی‌کند. این تمایز نباید در بازنویسی تصادفی از بین برود.
- عملیات سفارش داخل تراکنش انجام می‌شوند و کلید idempotency برای ایجاد سفارش وجود دارد. تغییرات موجودی باید همان مرز تراکنش و جلوگیری از ثبت تکراری را حفظ کنند.

### الزامات برای فازهای بعدی

- تمام مسیرهای create/append/cancel/restore/void/refund را جداگانه map و تست کنید.
- برگشت موجودی باید از مقادیر واقعی ثبت‌شده در ردیف سفارش استفاده کند؛ تغییر تنظیمات محصول پس از فروش نباید مقدار برگشت را تغییر دهد.
- وضعیت آماده‌سازی KDS نباید باعث کسر یا برگشت دوباره موجودی شود.
- پس از حذف Recipe، تمام importها، snapshotها، restoreها، تست‌ها و ستون/جدول‌های مرتبط باید بررسی شوند؛ پاک‌کردن صرف `recipe_snapshot` از insertها کافی نیست.

## 4. Recipe و Supplies: وابستگی اجرایی فعال

### Backend و schema

- `main/routes/index.ts` فعلاً routeهای `/api/supplies` و `/api/recipes` را ثبت می‌کند.
- `main/services/recipes.ts` recipe را به مواد اولیه وصل می‌کند و snapshot مقدارهای مصرف‌شده را می‌سازد.
- `main/services/supplies.ts` موجودی و گردش مستقل مواد اولیه را مدیریت می‌کند. نوع‌های گردش مواد اولیه شامل `receive`، `count`، `adjustment`، `waste`، `recipe_depletion` و `recipe_restore` هستند؛ این enum جدا از enum دفتر موجودی محصول است.
- در `main/db.ts` مهاجرت 88 جداول `supplies`، `supply_movements`، `recipes` و `recipe_items` را می‌سازد و مهاجرت 89 ستون `order_items.recipe_snapshot` را اضافه می‌کند. تعریف schema تازه‌نصب‌شده نیز این مدل‌ها را دارد.
- `main/routes/orders.ts` و `main/routes/index.ts` هنگام فروش و لغو از سرویس Recipe استفاده می‌کنند.
- `frontend/src/app/(dashboard)/inventory/page.tsx` در حال حاضر تب supplies را به‌عنوان پیش‌فرض باز می‌کند و تب recipes، فرم‌ها، APIها و گردش مواد اولیه را در خود دارد.

### تست موجود

`tests/recipe-order-lifecycle.test.ts` چرخه واقعی را آزمایش می‌کند: ساخت recipe، کاهش مواد اولیه در فروش، ذخیره snapshot، restore هنگام لغو، کاهش مجدد هنگام restore قلم، برگشت هنگام لغو سفارش، افزودن قلم به سفارش و تفاوت void با cancel.

**اثر:** این تست باید به مجموعه تست‌های بازنویسی چرخه فروش تبدیل شود تا بخش محصول/ledger همچنان پوشش داشته باشد. نباید کل تست حذف شود و در نتیجه لغو، برگشت یا idempotency بدون پوشش بماند.

## 5. میز و سفارش‌های نگه‌داشته‌شده

### وابستگی‌های Backend

- `main/routes/orders.ts` از `table_id` برای فیلتر و hydrate سفارش‌ها، رزرو مشتری، نوع `dine_in`، هزینه میز، تغییر وضعیت میز هنگام ثبت/تکمیل/لغو و تبدیل سفارش به takeaway استفاده می‌کند.
- `main/routes/tables.ts` مدیریت اصلی میزها و وضعیت‌های available/occupied/reserved/cleaning/held را پیاده می‌کند.
- `main/routes/held-orders.ts` مدل held order را با `table_id` ذخیره می‌کند؛ برای هر میز یک سفارش نگه‌داشته‌شده در نظر گرفته شده و وضعیت همان میز را تغییر می‌دهد.
- `main/db.ts` در مهاجرت 17 جدول `held_orders` با `table_id TEXT NOT NULL` می‌سازد. رابط کاربری هم state سفارش‌های نگه‌داشته‌شده را با کلید tableId نگه می‌دارد.
- `main/routes/index.ts` مسیرهای tables و held-orders را ثبت می‌کند و مسیرهای لغو/برگشت نیز وضعیت میز را آزاد می‌کنند.
- schema شامل `tables`، `floor_table_charges` و ستون‌های `table_charge` در چرخه سفارش/صورتحساب است.

### وابستگی‌های Frontend

- `frontend/src/components/layout/Sidebar.tsx` لینک میز را با `businessTypes: ['restaurant']` و setting `tables_required` فیلتر می‌کند؛ این فقط کنترل نمایش منو است.
- `frontend/src/app/(dashboard)/pos/page.tsx` انواع `Table`، picker و checkout میز، refresh میزها، شرط‌های `isRestaurant`/`tablesRequired` و held orders مبتنی بر میز را دارد.
- `frontend/src/app/(dashboard)/tables/page.tsx` صفحه مدیریت میز و نقشه سالن است.
- `frontend/src/lib/types.ts` نوع tenant را فعلاً `business_type: 'restaurant'` تعریف می‌کند؛ `Order` هم `table_id` دارد.
- گزارش‌ها queryهای اختصاصی میز دارند.

### وابستگی‌های گزارش و مبلغ

- `main/routes/reports.ts` در daily stats، تعداد میزهای اشغال‌شده، متوسط گردش میز و مدت اشغال فعلی را محاسبه می‌کند.
- همین فایل endpointهای گزارش میز و JOIN میز به سفارش‌های اخیر را نیز دارد.
- `table_charge` و `floor_table_charges` در محاسبات سفارش/صورتحساب، تخفیف و تبدیل dine-in به takeaway اثر دارند. هزینه‌های عمومی مانند ارسال و بسته‌بندی نباید همراه این منطق حذف شوند.
- تست‌های `tests/floor-table-charge.test.ts` و `tests/reports-daily-stats-table-turn.test.ts` رفتار فعلی را تثبیت می‌کنند.

**اثر:** حذف میز یک refactor انتها‌به‌انتهاست. تغییر تنها UI یا حذف route بدون بازنویسی held orders، queryها، محاسبات مبلغ، گزارش‌ها و داده‌های قدیمی باعث شکست runtime یا از دست‌رفتن داده می‌شود.

## 6. KDS و آماده‌سازی سفارش

### زیرساختی که ارزش حفظ دارد

- `main/services/kds.ts`: WebSocket، مدیریت اتصال، heartbeat، اعتبارسنجی token و ارسال به‌روزرسانی زنده.
- `main/routes/kds.ts` و `main/routes/kitchen.ts`: API خواندن سفارش‌ها و تغییر وضعیت اقلام.
- `main/kds-server.ts` و `frontend/src/app/kds-standalone/page.tsx`: مسیر اجرای نمایشگر مستقل.
- `frontend/src/components/kds/KdsWorkspace.tsx` و `KdsKanbanBoard.tsx`: UI نمایش تب/کانبان و تغییر وضعیت اقلام.
- `kitchen_stations` و `station_users`: ایستگاه‌ها، انتساب کاربران، دسته‌بندی‌های مجاز و تنظیمات چاپ.

### وابستگی‌هایی که باید تغییر کنند

- `main/routes/kds.ts` و `main/services/kds.ts` به `tables` JOIN می‌زنند تا `table_name` و `kitchen_station_id` را استخراج کنند.
- `main/routes/kitchen.ts` برای routing ایستگاه از `tables.kitchen_station_id` استفاده می‌کند.
- `main/routes/kitchen-stations.ts` در خواندن/حذف ایستگاه‌ها میزهای متصل را می‌خواند.
- UI کانبان در `KdsKanbanBoard.tsx` نام میز را نمایش می‌دهد.
- تست‌های KDS نشان می‌دهند برخی سفارش‌های بدون میز همین حالا هم در مسیرهای محدود به دسته/ایستگاه پشتیبانی می‌شوند؛ بنابراین میز تنها روش routing نیست.

**پیشنهاد پیاده‌سازی:** منطق دسترسی بر اساس نقش، دسته‌بندی، ایستگاه و WebSocket را حفظ کنید. مفهوم ایستگاه را در صورت نیاز به «ناحیه آماده‌سازی/انبار» تبدیل کنید و نام/شناسه محل آماده‌سازی را از میز جدا کنید. وضعیت آماده‌سازی باید از وضعیت مالی سفارش مستقل باشد.

## 7. دیتابیس، migration و schema-health

- `main/db.ts` رجیستری مهاجرت ترتیبی دارد؛ آخرین نسخه تعریف‌شده در commit بررسی‌شده 99 است.
- تعریف schema تازه‌نصب‌شده در `createSchema()` و migrationها هر دو باید با مدل مقصد سازگار شوند. حذف فقط از migration یا فقط از `createSchema()` باعث تفاوت نصب تازه و ارتقا می‌شود.
- migrationهای قبلی را تغییر ندهید؛ مهاجرت جدید افزایشی اضافه شود.
- `main/services/schema-health.ts` schema واقعی را با schema ایده‌آل ساخته‌شده از migrationها مقایسه می‌کند. جدول/ستون اضافه را خودکار حذف نمی‌کند و آن را برای بازبینی دستی گزارش می‌دهد.
- `main/db.ts` منطق بکاپ، restore، مهاجرت داده و بررسی موجودی محصول را هم در بر دارد. حذف جداول یا ستون‌های قدیمی باید پس از بررسی نسخه‌های قدیمی، داده‌های تاریخی، بکاپ/restore و رفتار restore انجام شود.
- جدول `orders` و `order_items` تاریخچه‌ای هستند؛ در صورت نیاز به حفظ سفارش‌های قدیمی، حذف قابلیت از UI نباید به پاک‌شدن بی‌برنامه اطلاعات گذشته منجر شود.
- تست‌های migration دفتر موجودی، backup/restore و schema-health باید در رگرسیون نهایی باقی بمانند.

|---|---|---|
| `tests/inventory-ledger.test.ts` | ledger، backfill موجودی قدیمی، افزایش/کاهش دستی، موجودی اعشاری، رد کاهش زیر صفر و رد مقدار منفی در PUT | حفظ پوشش ledger و به‌روزرسانی assertionهای منفی مطابق قرارداد جدید؛ افزودن فروش صفر/کمبود، race، cancel و retry |
| `tests/recipe-order-lifecycle.test.ts` | snapshot و مصرف/برگشت supplies در فروش و لغو/restore/void | جایگزینی پوشش Recipe با پوشش کامل موجودی محصول و چرخه سفارش، نه حذف کورکورانه |
| `tests/held-orders.test.ts` | نگهداری/بازیابی/حذف بر اساس tableId، اعتبارسنجی مقدار اعشاری و داده ورودی | تبدیل به شناسه مستقل held order و تست چند سفارش بدون میز |
| `tests/floor-table-charge.test.ts` | هزینه میز/طبقه، snapshot مبلغ، تخفیف و تبدیل takeaway | حذف فقط قواعد مختص میز و حفظ آزمون‌های مبلغ، تخفیف و صورتحساب عمومی |
| `tests/reports-daily-stats-table-turn.test.ts` | تعداد میز اشغال، گردش میز و occupancy | حذف خروجی‌های اختصاصی میز و تست صحت آمار عمومی فروش |
| `tests/tables-string-ids.test.ts` | API میز، شناسه‌ها، رزرو و دسترسی‌ها | حذف/جایگزینی پوشش با تست سفارش و مجوزهای عمومی |
| `tests/kds-integration.test.ts` | KDS مستقل، WebSocket، نقش‌ها و سفارش‌های tableless | حفظ و گسترش برای نمایشگر انبار/آماده‌سازی |
| `tests/kds-contract.test.ts` | قرارداد پاسخ KDS، نام میز، routing دسته/ایستگاه و محدودیت دسترسی | حذف وابستگی خروجی به میز و حفظ آزمون‌های مجوز و عدم تکرار routing |

نام تست‌ها از اسکریپت‌های `package.json` نیز ثبت شده‌اند. در این فاز **هیچ‌یک از تست‌ها اجرا نشده‌اند**؛ جدول بالا خلاصه‌ای از بررسی منبع تست‌هاست، نه گزارش موفقیت اجرای آن‌ها.

## 9. ماتریس «رفتار فعلی → هدف → خطر/تست»

| حوزه | رفتار فعلی مشاهده‌شده | رفتار هدف | خطر اصلی | آزمون ضروری |
|---|---|---|---|---|
| فروش بیش از موجودی | سرویس موجودی را با `Insufficient stock` متوقف می‌کند | فروش انجام شود و stock منفی شود | سفارش ثبت شود ولی موجودی/ledger با آن ناسازگار باشد | موجودی صفر، کمبود جزئی، مقدار منفی، فروش هم‌زمان |
| ثبت گردش | سرویس مشترک ledger موجود است | تمام تغییرات از سرویس مرکزی ثبت شوند | تغییر مستقیم cache بدون ledger | برابری stock با ledger و ثبت actor/reason/reference |
| لینک محصول | یک target مستقیم و factor معتبر | همان قابلیت بدون Recipe | کسر/برگشت از محصول اشتباه | factor، لینک نامعتبر، چرخه، لغو/restore |
| لغو و void | cancel موجودی را restore می‌کند؛ void طبق کامنت restore نمی‌کند | سیاست فعلی حفظ یا تغییر مستندشده | restore دوباره یا کمبود گردش | cancel تکراری، void، restore و تراکنش |
| Recipe | مصرف مواد اولیه در create/append/cancel | حذف از چرخه فعال | باقی‌ماندن import یا مصرف مخفی | فروش/لغو بدون جدول Recipe و صحت محصول |
| held orders | کلید و FK مفهومی مبتنی بر میز | شناسه مستقل سفارش نگه‌داشته‌شده | overwrite یا حذف سفارش اشتباه | چند سفارش هم‌زمان، stale delete، restore |
| میز و هزینه | میز، نوع dine-in و هزینه در totals/reports | بدون میز و هزینه مختص میز | تغییر مبلغ نهایی/مالیات/تخفیف | totals، bill sync، discount، refunds، گزارش |
| KDS | routing ترکیبی category/station/table | آماده‌سازی عمومی بدون میز | نشت مجوز یا حذف سفارش‌های tableless | نقش، category، station، WebSocket، cancel |
| migration | نسخه‌های ترتیبی و schema-health | schema یکسان برای نصب و upgrade | حذف داده یا ناسازگاری backup | ارتقا، نصب تازه، restart، backup/restore |
| WordPress/چاپ | مسیرهای جداگانه ولی متصل به سفارش | حفظ قابلیت‌ها | regression در sync و چاپ پس از تغییر مدل سفارش | create/edit product، online order، receipt/preparation print |

## 10. ترتیب اجرای پیشنهادی پس از فاز صفر

1. **فاز ۱:** تبدیل UI موجودی به موجودی محصولات با استفاده از API و ledger فعلی؛ پیش از حذف supplies، endpoint موجودی محصول باید مرجع واحد UI شود.
2. **فاز ۲:** تغییر قرارداد منفی‌شدن موجودی در سرویس، API محصول و سفارش؛ تست‌ها هم‌زمان با تعریف قرارداد اصلاح شوند.
3. **فاز ۳:** حذف Recipe/Supplies از مسیرهای runtime، ابتدا از سفارش و UI و سپس schema طبق migration جدید.
4. **فاز ۴:** بازطراحی held orders با شناسه مستقل و حذف میز از چرخه فروش/گزارش/هزینه.
5. **فاز ۵:** ساده‌سازی routing KDS به دسته/ناحیه آماده‌سازی و حذف وابستگی میز.
6. **فاز ۶:** تست end-to-end، نصب تازه و upgrade، backup/restore، ترجمه‌ها، WordPress، چاپ و بسته ویندوز.

## 11. محدودیت‌های این گزارش

- این گزارش از روی کد و تست‌های خوانده‌شده تهیه شده؛ تست runtime، build، lint و CI در این فاز اجرا نشده‌اند.
- جست‌وجوی کل repository باید در ابتدای هر PR اجرایی تکرار شود، چون فایل‌های جدید یا ارجاع‌های پویا/ترجمه‌ای ممکن است در فهرست اولیه نباشند.
- هیچ کد، schema، migration یا assertion تست در این مرحله تغییر نکرده است.
- نتیجه فاز صفر، مشخص‌کردن محل و نوع تغییرات لازم است؛ تأیید عملی رفتار نهایی به تست‌های فازهای بعدی وابسته خواهد بود.
